# fdindex tool contract (first cut)

The black-box compatibility contract with qartez v0.11.0. It comes from the public MCP tool schemas and from output observed on the flight-deck repo. No qartez source was read.

Every MCP tool is named `qartez_<verb>`, so existing skills, hooks and habits keep working. The CLI verb is `fdindex <verb>` (also `flightdeck index <verb>`, and `qartez <verb>` through the alias).

## Changes from qartez (required by the spec)
- **Paths.** Every path parameter accepts an absolute path or a path relative to the caller's cwd, which the shim sends. A relative path is never read against "the project root".
- **Output paths.** Every path in the output is absolute.
- **View header.** Every result starts with one line, e.g.:
  `view: /Users/me/Projects/Tessera/tessera (repo tessera, base 1a2b3c4, dirty 3 files)`.
  The parts: the absolute worktree; the repository's name; the first 7 characters of the base commit (`no commits` before the first commit, `not git` for a directory outside git); `clean`, or `dirty N files` where N counts the files that differ from the base.
  If a result draws on several views (see "Linked views"), each view other than the header's adds a line `linked view: <header text> via <manifest>` (or `dependent view: …`) after the header, and each row from one of them is labelled with its view.
- **Build state.** While the view is still building, the header adds ` index: building, N of M files` after the closing parenthesis. N and M count files of the view whose facts are stored.
- **add_root and workspace.** `qartez_add_root` and `qartez_workspace add` are accepted as hints that start a build early. They never change scope. `workspace remove` is accepted and does nothing.
- **Daemon down.** Every tool returns `state: UNAVAILABLE` plus a one-line reason. It never answers from a private index. (The CLI prints `state: UNAVAILABLE` and the reason to stderr and exits 3.)
- **Sandboxed client (Codex).** Under `codex exec -s read-only` and `-s workspace-write` (macOS seatbelt) `connect()` to the daemon socket fails with EPERM. A client treats `PermissionDenied` as a sandbox, not a missing daemon: it does not spawn one and reports `state: UNAVAILABLE` with `cannot connect to <socket>: Operation not permitted - a sandbox is blocking Unix sockets (for Codex: -s workspace-write -c sandbox_workspace_write.network_access=true, or run outside the sandbox); fall back to rg`. The MCP shim and `fdindex guard` (which still allows) say the same. `--no-start` / `FLIGHTDECK_INDEX_NO_START` is honoured by every client verb (query verbs, `mcp`, `session-start`); `status` never starts.

## Shared params
- `format`: `detailed` (the default), `concise` or `mermaid`. Only `deps` and `calls` honour `mermaid`. Every other tool rejects it with a clear error.
- `token_budget`: 4000 tokens by default, counted as 4 characters a token. The view header is not counted. A list tool (`grep`, `refs`, `calls`) cuts at whole rows and keeps its footer: `… N more (K of M shown, token_budget=4000); narrow with <arguments>; or raise token_budget`. `outline` shortens its page and gives the `next_offset`. Any other output is cut at a line and ends `… truncated: N of M lines shown (token_budget=4000); raise token_budget to see more`. `find` and `read` have their own bounds (`limit`, `max_bytes`) instead. See "Caps, ranking and ids".
- Aliases are accepted everywhere: `file_path` = `file` = `path`; `symbol` = `name` = `symbol_name`; grep's `query` = `pattern`.

## Mutators (preview by default; `apply=true` writes)
| tool | required | optional |
|---|---|---|
| replace_symbol | symbol, new_code (must begin with a definition introducer) | file_path, kind, apply |
| insert_before_symbol / insert_after_symbol | symbol, new_code (a trailing newline is added if missing) | file_path, kind, apply |
| rename | old_name, new_name | file_path, kind, allow_collision, apply |
| move | symbol, to_file (created if missing; importers are rewritten) | file_path, kind, apply |
| safe_delete | symbol | file_path, kind, force, apply |
| rename_file | from, to (also rewrites the Rust `mod` declaration; refuses `mod.rs`) | apply |

Rules for every mutator:
- If the name matches more than one definition, refuse and list the candidates with their files and kinds.
- Write only inside the view that answered the lookup (spec §5.5).
- Re-index the written files before returning.

## Observed qartez weaknesses not to copy
- It indexes submodules such as `vendor/boringssl` and `vendor/ghostty`, so they dominate the map and the stats. In the new engine a submodule is a separate repository.
- Swift files show 0 import edges, so deps, impact and blast all report 0 for Swift. The new engine should resolve Swift references by name within the module, so that deps and impact mean something.
- `find` reports every Swift `extension X` as a separate `class` named X. Keep extensions, but give them their own kind, `extension`.

## As built: arguments and output the table above leaves open

- **find.** `limit` (default 50) applies to the exact search as well as the regex search, because an exact `view` in an Elm repository matches a thousand modules. Matches are ranked (exported, then PageRank). A cut ends `… N more match(es) (K of M shown, most important first); narrow with kind= or file_path=; or pass limit=M to see all`. `detail` defaults from the hit count: up to 10 matches print a block each, more print one row each (`name kind path [Ls-Le] status`, as `grep`). A match block adds `Module:` (Elm) and `In:` (the enclosing type) lines when they apply, and `Id: path:Type.name` unless `format=concise`. A qualified name (`Expression.Node.toString`, `store::open`) matches by module, enclosing type or file stem. Package symbols (see "Package symbols") follow the repository's matches inside the same limit, as `map (function)` / `Package: elm/core@1.0.5 List.map` / `Signature: (a -> b) -> List a -> List b` / `Status: package`. An exact search that matches nothing keeps its `No symbol found with name 'X'` lines and, when any symbol shares a word with the name, appends `Closest by words (w1 w2):` and up to 10 grep-style rows ranked by words (below). A regex search has no fallback.
- **grep.** `query` is a case-insensitive prefix match on symbol names (`Foo` and `Foo*` are the same); `regex=true` makes it an unanchored case-insensitive regex. Rows: `name  kind  path [Ls-Le]  exported|private`, ranked by the file's PageRank, then name, path and line (exact-name-first was measured and cost 1.4 points of File@10 on tessera; `find` is the exact-name tool). `limit` defaults to 50; the footer hint is `kind=, a longer prefix, or regex=true`. `detail` defaults to `full` (each row followed by its signature) up to 5 hits and `rows` past that. A `near` seed set reorders on top of this order. `search_bodies=true` reads the files of the view from disk and reports lines inside function-like bodies: `path:Lline in function (kind): text`, files by PageRank, lines in order.
- **grep across worktrees.** `search_bodies=true` with `worktrees=all` (every worktree of the caller's repository the index has a record of, plus the caller's own) or `worktrees=[paths]` searches all of them in one call. `worktrees` without `search_bodies` is a `BAD_REQUEST`; leaving it out keeps the single-view search unchanged. Each distinct blob is read once, from one worktree whose file still hashes to that blob (else from `git cat-file`), and its hits are fanned out to every worktree holding it. No graph is built, so the graph cache does not grow, and no per-worktree read gate is held. The header's second line is `worktrees: N searched (repo R), B distinct blob(s) scanned, K refreshed from git`, followed where they apply by `, X read from git`, `, U unreadable (changed again since recorded)`, `, S skipped` and one `skipped: <path> (<reason>)` line each (`gone`, `another repository`, `not a git worktree`, or the error). Rows are grouped by file: a line `[N worktrees: a, b, c, d, e, f +k]` (labels are directory names sorted, or full paths where two share a name; six at most) heads the `path:Lline in function (kind): text` rows of that blob at that relative path. `limit` counts rows (distinct blob, path and line), not worktrees. The body rule is the single-view one, so the rows are the union of a single-view search of each worktree.
  Freshness: the caller's worktree, worktrees with a view kept by the watcher, worktrees the store has no row or no tree for, worktrees whose HEAD moved, and worktrees with any file (or directory holding one) modified after their row was last written are re-read from git first, as a single-view request would. Every other worktree is answered from its recorded tree and overlay. `refresh=true` re-reads every worktree from git (measured at 1.3-1.5 s of `git status` for 85 worktrees). An edit made in the same second the worktree was last recorded can be missed until it is next refreshed. A blob with matching lines but no stored facts (a worktree whose build has not reached it) is counted in a `note:` line instead of being placed in a body.
- **grep, ranked by words.** A query that contains whitespace (and is not `regex=true`), or any query with `rank=true`, is a ranked search: no symbol name has a space, so a sentence never matched a prefix (it answered `No symbols match` every time). The query's identifier-shaped words of 3 or more letters (at most 12, stopwords such as `the`, `fix`, `add` dropped) are split on camelCase, snake_case and separators and lightly stemmed (`exports` → `export`, `queries` → `query`, `loading` → `load`, `refused` → `refus`). Each symbol except impls and fields is a document of three fields: the words of its name, of its parent's name, and of its file's path plus Elm module, split and stemmed the same way. Score: BM25F, k1 1.2, b 0.75 per field, weight 1 per field, idf `ln((N-df+0.5)/(df+0.5)+1)`. Output: `Ranked by words: w1 w2 (N matching symbol(s), best first)`, then rows in the prefix format, best first, `limit` rows (default 20), then `… N more; pass limit=N to see more`. When 3 or fewer symbols match, each row is followed by that symbol's code as `N | source` lines (at most 80 per symbol). The answering view is ranked first, then each linked view with its own index (`[view: …]` rows): scores from different views are not compared. Exact or prefix hits are never put in front of ranked rows (measured on 200 tessera commit subjects: File@10 40 with words alone, 9.5 with exact `find` hits first). When no symbol has any of the words, function bodies of the answering view that contain them are searched from disk instead: `No symbol has the words a b; function bodies that contain them:`, one `path:Lline in function (kind): text` row per enclosing function (its first matching line), most distinct words first. A prefix search with no match answers ``No symbol names start with `X`; closest by words:`` and up to 10 ranked rows, and keeps ``No symbols match `X` `` when no symbol shares a word either. The word index is built per graph on the first ranked query (median 20 ms and 4.7 MB for an tessera graph of 44k symbols, 24 ms and 4.6 MB for flight-deck, measured at load 11-25) and counted in the graph's byte estimate once built; an edited view gets a new one.
- **History tier (find, grep).** Both tools append a `History matches for 'q' (by the subjects and changed lines of the last N commits):` section when the query has a space (prose) or the name search found nothing; `history=true` forces it and `history=false` turns it off (CLI `--history`). It never runs for `regex=true` unless asked, nor for `search_bodies=true`. Rows: `name  kind  path [Ls-Le]  — <commit subject> (<short id>)`, best first, at most 10 (`limit` raises it to 50); a file gets its own row `(file)  path  — subject` where its document ranks, unless one of its symbols is already listed above it. Ranking is BM25 (k1 1.2, b 0.75) over per-symbol documents built from the last 2000 non-merge commits reachable from the view's base commit that changed an indexable file: each commit's subject and up to 64 words of its changed lines (256 for the file) are added to the innermost symbols its `-U0` hunks overlap (old lines against the old blob, new lines against the new) and to the file. The subject line shown is the best-matching commit's. Words are split at camelCase and non-alphanumerics, lower-cased, stopwords dropped, plurals folded (`refuses` -> `refuse`). Commits that change more than 40 indexable files are skipped, renames are not followed, and symbols are matched to the view by path and qualified name (`Store.open`), so a symbol that was renamed or deleted drops out. The index is per repository, built on a background thread the first time a query wants it and again when HEAD moves (a fast-forward of up to 200 commits adds only the new commits, until the window is 10% past 2000; anything else rebuilds); until the first build ends the section is `history: indexing this repository's commits; retry shortly…`, and after a HEAD move the previous index answers. Nothing is written to the store: historical blobs are parsed in memory when the store does not already hold their facts. Only the answering view is searched, not linked views. No match prints `No history matches for 'q' in the last N commits`. The section is a tier of its own: after the ranked rows of a ranked `grep`, and after the closest-by-words rows of a zero-hit `find` or prefix `grep`, never merged into them.
- **read.** `symbol_name` / `symbols[]` (each a name or an id, with an optional `file_path`) print each definition as `// name kind @ path:Ls-Le` followed by `N | source` lines; `context_lines` adds lines around it; an ambiguous name prints a warning listing the definitions' ids and up to 5 definitions, then `// … N more definition(s)` if there are more. A symbol is never windowed: its whole span is printed up to `max_bytes` (a 100-line cap hid the edit site in half to two-thirds of long gold symbols). With only `file_path` the file is read from disk, so it works on any file under any path: `start_line` (alias `offset`, `start`), `end_line` (alias `end`), `limit`, header `// path [L2-L9 of 120]`. A ranged read never waits for a build. With no range and no `max_bytes`, a source file (one a language module handles) of more than 150 lines returns the header `// path [L1-L100 of N]`, `// outline (K symbols):` and the outline rows (100 at most, then `// … more symbols: outline file_path=… offset=100`), lines 1-100, and `… lines 101-N not shown: pass symbol_name= (or an id path:Name), start_line/end_line, or limit= to read on; max_bytes= reads the whole file`. Such a read waits for that file's own priority slice (for the outline); if the file is still not parsed, the window comes without an outline. Any other file (Markdown, config) is read whole as before and never waits. Output is cut at `max_bytes` (25000) and the cut says where to go on: `… truncated at max_bytes=25000 inside name [La-Lb]: pass file_path=… start_line=K end_line=b to read on, or raise max_bytes`, or `pass start_line=K (or limit=) to read on` outside a symbol.
  `with` (a list, or a comma-separated string) attaches context to each definition read by symbol; the only value is `callers`, anything else is `BAD_REQUEST`, and so is `with` on a line-range read. `callers` prints, between the `// name kind @ …` header and the body (so a body cut at `max_bytes` keeps it), `// callers (shown of total):`, then per caller `// ← name @ path:Lcall · signature` (marked `(matched by name)` when the edge is a name guess) and `//   Lcall | <trimmed source line of the call>`, up to 5 callers: resolved before matched-by-name, then by PageRank, with callers in test files last (they are not dropped, unlike `calls`). More callers end `// … N more: \`calls name=X direction=callers\``. A definition that is not function-like prints `// callers: X is a <kind>, not function-like; \`refs\` lists its uses`. Off by default: retrieved context is not always worth its tokens.
- **deps.** `# Dependencies: <path> (blast →N)`, then `Imports from (n):` rows `-> path (import: spec)` and `Imported by (n):` rows `<- path (import: spec)`. `concise` drops the specifiers. An import that leaves the worktree through a manifest is marked `external`. `mermaid` prints `graph LR` with absolute paths as labels.
- **stats.** Without `file_path`: `files=N (src=A/test=B) loc=L syms=S edges=E`, a `languages:` list and the `most imported:` files. With `file_path`: `path`, `LOC | Symbols (n exported) | Imports | Importers`, `Language | PageRank`.
- **impact.** `include_tests` defaults to **false** (a file is a test by its path: a `test`/`tests`/`spec`/`__tests__` directory, `x_test`, `x.test.ts`, `XTests.swift`). Sections, in order:
  - `Seeds: <file>, and the worktree diff: a, b`, only when the view's worktree has changed files (its overlay against the base commit, deletions included) and `seed_diff` is not `false`.
  - `Ranked impact (N: importers and co-change partners interleaved; co-change from the last C commits):` rows `path  (reasons)`. Two lists are alternated, the next unseen file of each in turn, so any prefix holds about half of each and the longer list fills in when the other runs out (Gethers et al., ICSE 2012: N/2 from each source, not a blended score). List A is every transitive importer of the file, nearest first, then by PageRank. List B is co-change partners of every seed by confidence `P(partner changed | seed changed) = together / touches(seed)`, each partner at its best seed, then by support, then by path. A file in both lists appears once with both reasons: `importer depth 2; co-changed 3/7`. A partner whose best seed is a diff file names it: `co-changed 2/2 with src/edited.ts`. Seeds are left out. If co-change cannot be computed the heading says `importers only; co-change unavailable: <why>`.
  - `Tests (n):` every test linked to a seed, never capped, listed whatever `include_tests` says, including tests the worktree diff already edits (only the file asked about is left out): first tests whose name names a seed (the stem without `Test`/`Tests`/`Spec`/`_test`/`test_`/`.test`/`.spec`, matched case-insensitively and without `_`/`-` to a seed of the same language whose stem is unique among that language's sources, or a marker-free file under a test directory with the seed's stem), then tests that import a seed directly (`importer depth 1`), then tests that co-change with a seed (`co-changed t/n`). Each test appears once, with every reason.
  - `Direct importers`, `Transitive blast radius` (each ranked by directory proximity to the file: shared leading directories, half a point less for a test file; then PageRank, then depth, then path; a `near` seed set reorders on top), `Hot symbols in this file` (heading `(5 of N)` when it cuts).
  Each capped list shows 30 rows and then `… N more` (the importer and radius lists say `… N more (ranked by directory proximity); narrow with …`). Co-change counts commits among the last 2000 non-merge commits reachable from the view's base commit, skipping commits of more than 40 files and files no language module handles; `touches` counts every such commit that changed a file, alone or not. A partner needs at least 2 shared commits.
- **impact pending=true** (CLI `--pending`; not in qartez). Follows up the worktree's uncommitted diff instead of one file; `file_path` is optional and narrows to one changed file, and `include_tests` defaults to **true** (a test's call site needs the edit too). It compares each changed file's symbols in the base commit with the worktree's, paired by parent chain, name and kind family (an Elm value that gains an argument goes from const to function and stays the same symbol). A symbol is listed when its *call shape* changed, or when it is gone (renamed, deleted, moved). The call shape is the signature with whitespace collapsed; in Rust, TypeScript, JavaScript and unannotated Elm the parameter names are dropped (`fn f(a: u8)` and `fn f(b: u8)` are the same shape), while Python and Swift keep them (keyword arguments, labels); Elixir's `name/arity (spec)` and Elm's type annotation carry no names already. For each listed symbol it prints `Changed: name (kind) path:Lline` with `was:` and `now:` signature lines (or `Removed or renamed: …, was path:Lline` and `was:`), then `Not yet edited (N; M already edited):` and one row per site: `path:Lline kind[ in enclosing][ (matched by name)| (matched by text)]: \`code\``, where kind is `call`, `use`, `type` or `implementer`. Sites come from: the symbol's resolved references in this view and the linked ones; for a removed symbol, its references in the base graph, carried to their worktree line through the diff; the same-named members of types that extend or implement a changed member's trait, interface or class; and a text scan for `name(` in the files that import the symbol's file (and the files already holding a reference), which finds calls the parsers do not see (inside a Rust macro's arguments, a TypeScript template substitution). The text scan skips Elm, comment, import and definition lines, matches inside a `"` string (or `'` string in TypeScript, JavaScript, Python and Elixir), lines already covered by a reference, and any file that defines its own function of that name. A site is *edited* when the line diff (an LCS of the base blob against the file on disk) marks its line, or one of the 2 lines after it, as changed; the window stops before the next site in the same file, so editing one of two adjacent calls leaves the other pending. A site in another view (not this worktree's diff) is never edited. Order: symbols with the most pending sites first; within one, resolved before matched by name before matched by text, then call, use, type, implementer, then file PageRank. Each list shows `limit` rows (default 30), then `… N more (pass limit=N to see all, or file_path to follow one changed file)`. A clean view, or one without a base commit, answers `Pending edits: none (…)`; a diff that changes no call shape answers `Pending edits: no signature changed in the diff (N file(s) differ from the base); nothing to follow up.`
- **refs.** `symbol` (aliases `name`, `symbol_name`), optional `file_path` and `kind` to narrow, `include_tests` (default true), `transitive`. Each candidate definition prints `Symbol:`, `Defined in:`, then references grouped by file as `L144 call in enclosing_fn`; a reference matched only by a unique name is marked `(matched by name)`. `transitive=true` appends `Transitive dependents`. A package symbol (see "Package symbols") is a candidate of its own, listed first: `Symbol: field (package function)`, `Defined in: package elm/json@1.1.3 Json.Decode.field`, then its references in the answering view in the same shape. Files are ranked: the defining view first, then directory proximity to the definition, then PageRank (a `near` seed set reorders on top). A budget cut keeps whole rows (a file heading only with its first reference) and ends `… N more reference(s) (K of M shown, token_budget=…); narrow with file_path= / kind= / include_tests=false; or raise token_budget`, naming only the arguments not already given. `transitive=true` dependents are ranked like `impact`'s radius, 30 rows, then `… N more`.
- **Swift receivers.** In `recv.m()` with an expression receiver, the type of `recv` comes from declarations alone, first match wins: `self` is the enclosing type and `super` its superclass; a lowercase name is the innermost visible binding (a parameter, `let x: T`, `let x = T(...)` or `T.init(...)`, `if`/`guard let`, `for x in` an array) or else a property of the enclosing type or its supertypes; `T(...)` builds a `T`; `f(...)` returns `f`'s declared type when its overloads agree; each later segment is typed through the declared property and return types of the view. `m` is then looked up on that type and its supertypes and protocol extensions, among the modules the file sees, and printed like an exact match. A typed receiver whose type has no such member (a platform type, a method inherited from a platform class) has no target, as does a receiver built from a type the repository does not declare (`Text(..).font(..)`). Only an untyped receiver (a closure parameter, a subscript) falls back to a unique member name, marked `(matched by name)`; such a guess is listed by refs and calls but draws no file edge, so deps, impact, blast and the PageRank in map and stats do not count it.
- **Swift index store (engine layer, not yet applied by the daemon's tools).** `Engine::precise_graph` reads the build's index store when one describes the worktree (`<worktree>/DerivedData/Index.noindex/DataStore`, `.build/*/index/store`, or a `~/Library/Developer/Xcode/DerivedData/*` folder whose `info.plist` names the worktree) through `libIndexStore.dylib`, opened at run time from the selected toolchain, Xcode or the Command Line Tools; without it there is no layer. For each Swift file no newer on disk than its newest unit, a reference the compiler resolved replaces the heuristic answer with confidence `precise`, including "outside the repository" (no target). Files edited since the build, and every other view, keep the heuristic answers. Reading Flight Deck's store takes 0.6–2.5 s.
- **calls.** `depth` defaults to 1. More than one function-like definition and neither `file_path` nor `kind` gives the refusal with `candidates:`. At `depth` 0 and 1 the output is `Callers (n):` / `Callees (n):` rows `[d1] name (kind) path:Lline`. `mermaid` prints `graph LR` of the edges at any depth. At depth 1 the rows are ranked per depth by directory proximity to the target, then PageRank (a `near` seed set reorders within each depth). A cut makes the heading `Callers (50 of 80):` and ends the section `… 30 more (50 of 80 shown); narrow with direction=callers / depth=1; or pass limit=80 to see all` (or `raise token_budget` for a budget cut). The refusal lists each candidate as `- path:Type.name (kind) [Ls-Le]`, an id to pass back as `name`.
  At `depth>=2` (detailed and concise) the output is a tree of signatures, never bodies: `Call tree for name (kind) @ path:Ls-e`, the target's signature, a one-line legend, then per direction `Callers (tree, depth d, N distinct):` and rows `- name path:Lcall · signature` (a caller row names its call site, which is in the caller's file) or `- name path:Ldef call@Lcall · signature` (a callee row names the callee's definition and the call's line in its parent), each indented two spaces per level under the function it calls or is called by. Signatures are folded to one line and cut at 120 characters. Each function is printed in full once, at the shallowest level it is reached, under the parent that first reaches it in breadth-first order; any other edge to it is a short row ending `↑`, and an edge back to a function on its own branch (the target included) ends `↺`. Rows under a parent are ordered resolved before matched-by-name, then by PageRank, then by path and line; each neighbour appears once per parent, at its first call site.
  `limit` counts functions (full rows), not `↑`/`↺` rows. Each direction goes as deep as its levels above the last fit `limit`; the last level is filled in row order up to `limit` and the rest end `… N more row(s) at level d; pass limit=M to see them`. If the levels above the last already exceed `limit`, that direction shows one level less, and its title says `depth d of k; level d+1 exceeds limit=L`. Then, while the whole text exceeds `token_budget`, the deepest level of every direction goes (`… exceeds token_budget=T`); only at depth 1 is the text cut by the usual truncation.
- **map.** `Codebase: <name> (N files, M symbols indexed)`, then `# | File | PageRank | Exports | Blast` rows, then (detailed) each file's exported signatures, six at most. Test files and files without symbols are left out unless `all_files`. `by=symbols` ranks symbols (plain symbol PageRank, never personalized). `boost_terms` multiplies by 5 the rank of files whose path or symbol names contain a term. `with_health` is accepted and ignored.
  - **Seeded (personalized) map.** When the caller passes `boost_files`, or else when the worktree has uncommitted changes (the service passes the modified files as `diff_files`; at most 50, never for a tree without git), files are ranked by a personalized PageRank that restarts at those seed files: edges run from a resolved reference to its definition and back (the reverse at 20 times the forward weight), weighted per name as Aider's repo map does, without its mentioned-identifier and chat-file multipliers (`graph/ppr.rs`). The output gains a `Seeds: <abs path>, …` line before the table, the seeds are left out of the rows, and test files and files without symbols are shown as if `all_files` were set. `boost_terms` still multiplies after the walk and never seeds it. `personalize=false` turns all of this off: `boost_files` then multiplies a file's rank by 10, as qartez did. With no seed the map is the plain PageRank, unchanged. Measured on the eval's seeded tasks (first gold file as the open file): File@10 0.3 -> 32.2 (tessera), 2.7 -> 57.2 (flight-deck); the first seeded `map` on a new graph builds the walk's adjacency (about 40 ms on tessera), later ones take about 1 ms more than an unseeded map.
- **PageRank values** (`map`, `stats`, the guard's `pagerank`, and the ordering they drive) are solved to an L1 tolerance of 1e-6 (damping 0.85; dangling files spread their rank evenly), so they sit within about 1e-5 in total of the exact ranks and two graphs of the same content agree to that, whichever cached graph a warm start began from. The earlier fixed 30 sweeps left ranks up to 5e-4 (L1) from the fixed point on tessera, so a rank printed to four decimals can differ in its last digit from before.
- **near** (`find`, `grep`, `refs`, `calls`, `impact`; `src/near.rs`). Orders rows by graph distance from a seed set, so a cap (`limit`, the 30-row lists, `token_budget`) keeps the rows next to the work instead of the popular or alphabetically first ones. Seeds: `near` lists files (absolute, or relative to the cwd) or symbol names (the files that define them). Without `near`, the seeds are the worktree's changed files plus the last 8 files `read` or `outline` looked at in that worktree (in memory, per daemon), at most 32 files. `near: []`, `near: false` or `near: none` turns ordering off; so does a seed set that names no file of the view, so a clean worktree nobody read in answers exactly as before. Score per row: 0.6^hops, where hops is the breadth-first distance from the nearest seed file over file imports in both directions (a seed is 1; beyond 3 hops, 0), plus 0.5 when a definition calls into a seed file or is called from one, plus 0.15 × its log-PageRank scaled to [0, 1]. Rows are sorted by it, stably, so equal scores keep the tool's own order (`grep` alphabetical, `calls` by depth first: nearness only reorders within a depth). Only the answering view's rows are scored; linked views' rows score by PageRank alone. A reordered result says so on the line after its title: `(ordered by nearness to N seed file(s); near=[] turns this off)`. The line names no paths, because every path in a result is a row.
- **add_root / workspace.** `path` (aliases `root`, `dir`, `file_path`; default the cwd) starts a build without waiting. `workspace action=remove` replies that there is nothing to remove.
- **Admin tools** (not part of the qartez surface): `status` (also as `data`), `hello`, `shutdown`, `build <path>` (waits for the whole build, up to 10 minutes), `gc` (collect and vacuum every repository's store: queued for the maintenance thread, or run before it answers with `--now`; `gc <path>` does that path's repository only and waits).

## Package symbols

A reference into a dependency resolves to a symbol of that package version, read from the package manager's own cache (read-only, never written) and shared by every view on the machine. Elm and npm (TypeScript, TSX, JavaScript) so far; the representation (manager, package, version, module, name, the way SCIP names symbols) leaves room for Cargo, Hex and SwiftPM caches.

- **Where from.** The nearest `elm.json` above the file: an application's `dependencies.direct` and `test-dependencies.direct` (exact versions; `indirect` dependencies cannot be imported), a package's `dependencies` and `test-dependencies` ranges (the highest installed version in each). Each version's `docs.json` under `$ELM_HOME/0.19.1/packages` (`ELM_HOME` defaults to `~/.elm`). A version with no `docs.json` (downloaded, never built) is skipped and its references stay unresolved; `status` lists it as `no docs.json: author/name@version`.
- **Implicit imports.** Every Elm file imports what elm/compiler 0.19.1 imports by default: `Basics` exposing everything; `Debug` and `Tuple`; `List` exposing `(::)` and the built-in `List` type; `Maybe` exposing `Maybe(..)`; `Result` exposing `Result(..)`; `String` and `Char` exposing their types; `Platform` exposing `Program`; `Platform.Cmd as Cmd` exposing `Cmd`; `Platform.Sub as Sub` exposing `Sub`. Explicit imports add to these.
- **Precedence.** A definition in the file, an import of a repository module, and a cross-repo link come first; a package name comes next and always beats a unique-name guess (`(matched by name)`). In a type position the constructors a `Type(..)` import exposes are not candidates (`String` in a signature is elm/core's type even when a repository constructor is called `String`).
- **What it changes.** `find` and `refs` list package symbols: for a qualified name (`List.map`, `Json.Decode.field`), or for any name no repository symbol matches. They are never ranked: no package node or edge enters `map`'s file or symbol PageRank, and a package import adds no edge to `deps`/`impact`.
- **Matched by name.** The unique-name fallback only considers definitions in the referring file's language family (TypeScript, TSX and JavaScript are one family; every other language is its own), and an Elm type position never falls back to a constructor.
- **npm: where from.** A bare import specifier (`react`, `@scope/pkg/sub`, `node:path`; ES `import`, `export … from` and CommonJS `require`) resolves the way the TypeScript compiler resolves it for types: the nearest `node_modules/<name>` above the importing file, never above the worktree root; the package's `exports` map (conditions `types`, `typings`, `import`, `node`, `module`, `default`, `require`, in that order, and one `*` pattern), else `types`/`typings`/`main`/`index.d.ts`, a `.js` target meaning the `.d.ts` beside it. A package without declarations falls back to `@types/<name>` (`@scope/x` is `@types/scope__x`); a name no package provides falls back to the `declare module "<name>"` blocks of the nearest `@types/node` (`path`, `node:fs`, `assert/strict`). A package whose real directory is under no `node_modules` (a workspace or `file:` link into a repository) is source, not a package, and stays unresolved here. JavaScript files without declarations, and `tsconfig` `paths`, are not read.
- **npm: what binds.** The declaration files are read with re-exports followed (`export { a as b } from`, `export *`, `export * as ns`, `export =`, `export default`, `import x = require()`, across packages), and a symbol is the declaration it reaches: vitest's `expect` is `vitest@3.2.7 vitest.globalExpect`, its `describe` is `@vitest/runner@3.2.7 @vitest/runner.describe`. A named import binds that export, a default import the default export (or the `export =` value), `import * as ns` and `const ns = require()` the module. One level of members resolves (`vi.fn`, `fc.constantFrom`, `assert.strictEqual`, `path.join`, `React.useState`, the type `React.FC`): a namespace's declarations, a class's members, or the members of a constant's declared type (interfaces it extends, intersections, object literals in it or passed as type arguments, `typeof x`; `Omit`/`Pick`/`Partial`/`Required`/`Readonly` read as their first argument). Global declarations (`Array`, `Promise`, `describe` without an import) are not bound.
- **Freshness.** A committed `elm.json` edit is seen, because a new commit gets a graph of its own. An uncommitted one is not: `elm.json` is not an indexed file, so it is not part of a worktree's overlay and the base commit's resolutions are reused (the same holds for `source-directories` today). A package built after a graph was resolved is seen by the next graph resolved from scratch. The same holds for `node_modules`: an install is seen by the next graph resolved from scratch, and a declaration file already parsed for a package version is not re-read (`package.json` is re-read when its modification time changes). Clean worktrees of one commit share one graph, so a worktree without `node_modules` shows the package symbols another worktree's install resolved.

## Caps, ranking and ids

- **Rank, then cut.** Every list is ordered before any cap or budget can drop rows from it: `find` by export and PageRank, `grep` by file PageRank, `impact` and `refs transitive` by directory proximity, `refs` files by the defining view then proximity, `calls` by depth then proximity. A `near` seed set reorders each of these on top, stably (equally near rows keep the order here), and `impact`'s `Ranked impact` list keeps its interleave unless `near` is passed explicitly. Measured on 200 commits each of tessera and flight-deck, proximity order keeps 75.1% / 77.5% of the files later co-edited with the anchor inside `impact`'s two 30-row caps, against 66.5% / 65.3% for the old order (direct importers by path, radius by PageRank).
- **Never silent.** A list cut by its `limit`, a fixed cap or the `token_budget` ends with `… N more`, how many are shown of how many, the arguments that narrow it, and then `pass limit=M to see all` or `raise token_budget`.
- **Readable ids.** A symbol id is `path:Name`, or `path:Type.name` for a member (`/r/src/store.ts:Store.open`). `find` prints one per match (`Id:`); the `calls` refusal and the `read` ambiguity warning list candidates as ids. Every symbol argument (`find`, `read` with `symbol_name` / `symbols[]`, `refs`, `calls`) accepts an id: the path part must contain a `/` or an extension and is read against the caller's cwd like any path, and it selects the view as `file_path` would. An explicit `file_path` wins over the id's path. `::` is never the separator, so `store::open` stays a qualified name.
- **detail.** `find` and `grep` take `detail` = `full` or `rows`; it defaults from the hit count (full up to 10 matches for `find`, up to 5 for `grep`).

## When a request waits for a build

An unknown view is registered and built with the requested paths first (the files and their direct imports). `outline`, `read` of a symbol and a whole-file `read` (no range, no `max_bytes`, which leads with the outline) are answered as soon as that slice is stored; a ranged `read` never waits. Every other tool needs to know who imports or calls what, and a partial graph would answer "no importers" for a file whose importers are not parsed yet, so it waits for the whole view. Both waits stop at 10 seconds (configurable with `--build-wait-ms`; a request may ask for less with `build_wait_ms`; never more than 30 seconds). After that the request is answered from what is stored, with `index: building` in the header. A request that names a file that is not parsed yet gets `state: BUILDING` instead of a "no such file" error. The build carries on in the background and concurrent requests for the same worktree share it.

## Wire protocol

Newline-delimited JSON over a Unix socket (mode 0600). Default path: `<store>/fdindex.sock`, where the store is `~/Library/Application Support/FlightDeck/index` on macOS and `$XDG_DATA_HOME/flightdeck/index` on Linux (the Linux default socket is `$XDG_RUNTIME_DIR/fdindex.sock`). `--store`, `--socket`, `FLIGHTDECK_INDEX_DIR` and `FLIGHTDECK_INDEX_SOCKET` override them. The path must fit a Unix socket (about 100 bytes); a longer one is refused with that message.

```
-> {"v":1,"id":7,"cwd":"/abs/cwd","seq":12,"tool":"find","args":{"name":"update"}}
<- {"id":7,"ok":true,"text":"view: …\nFound 2 match(es) for 'update':\n…"}
<- {"id":7,"ok":false,"error":"…","state":"BUILDING"}
```

- `v` is the protocol version the client speaks (now 1). A daemon that does not speak it answers `state: VERSION_MISMATCH`. `tool: "hello"` returns `data: {version, protocol, pid}`; clients call it first.
- `cwd` is required and absolute for every tool that reads code. `seq` is recorded per cwd (the watcher step will use it for read-your-writes). `id` is echoed.
- Tool names may carry the `qartez_` prefix.
- `state` is one of `UNAVAILABLE` (client-generated: the daemon cannot be reached or started), `BUILDING`, `BAD_REQUEST`, `VERSION_MISMATCH`, `ERROR`.
- A connection answers in order. Two requests in flight need two connections. A request line over 4 MiB is refused and the connection closed.
- `status` returns `text` and `data`: pid, uptime, RSS, request and error counts, blobs parsed, the views known (worktree, repo, base, dirty files, requests, idle seconds, whether the view is kept between requests and swept by stat, with the files and directories swept, the last sweep's milliseconds and how long ago it last found a change), builds in progress (phase, done, total), graph cache (count, charged bytes, facts bytes (the blob facts any graph still holds plus each repository's reference-name pool, counted once per repository), distinct shared blocks and their bytes, budget, evictions, heap limit) each repository's store file size and free pages, each repository's history-tier index (`data` only: commit, commits, approximate bytes, build milliseconds, whether it was an incremental update, whether a build is running, the last failure; dropped when the repository's last worktree is swept), the package views (versions parsed, names, versions skipped for want of a `docs.json`), the ref watcher (repositories watched, events seen) and the garbage collector (runs, bytes reclaimed in total, and the last run's repositories, worktree rows, trees and facts collected, pages vacuumed, bytes before and after).
- `shutdown` answers and exits.

## CLI

`fdindex [--store DIR] [--socket PATH] [--cwd DIR] [--json] <tool> [first-arg] [--flag value]…`. Flags become arguments as written (`--file-path x` is `file_path`, `--build-wait-ms` is `build_wait_ms`). A flag without a value is `true`; the boolean flags (`--regex`, `--transitive`, `--pending`, `--include-tests`, `--all-files`, `--search-bodies`, `--rank`, `--refresh`, …) never consume the next word. A repeated flag becomes a list. The first positional argument fills `name` (find, calls), `symbol` (refs), `query` (grep), `file_path` (outline, deps, impact, stats, build, gc, add_root); `read` takes a file if the argument contains `/` or is a file, else a symbol. If no daemon answers, the CLI starts `fdindex daemon` detached and retries. `fdindex status`, `fdindex stop` (returns when the daemon has exited) and `fdindex daemon [--memory-mb N] [--graph-budget-mb N] [--build-wait-ms N] [--watch-hours N] [--no-watch]` manage it (`--watch-hours`, default 6: how long an idle worktree keeps its in-memory view; `--no-watch`: every request reads `git status` and no ref watcher runs).

Management verbs (top level, and `fdindex service <verb>`): `status` (the daemon's report, exit 3 when it is not running; **never starts it**, unlike every query verb; `--json` prints the raw reply), `stop`, `start`, `restart`, `install`, `uninstall`. `fdindex mcp [--no-start]` is the MCP shim.

## MCP shim (`fdindex mcp`)

A stdio MCP server, newline-delimited JSON-RPC 2.0 (`initialize`, `notifications/initialized`, `tools/list`, `tools/call`, `ping`; empty answers for `resources/list`, `prompts/list`). It holds no index and opens no database. Server name `flightdeck-index`; its `instructions` say, truthfully, that this is Flight Deck's machine-wide index, which tool answers which question (where is X defined: `find`, or `grep` for part of a name or body text; show code: `read`, `outline`; who uses X: `refs`, or `calls` for call edges and chains; what could break: `impact`, or `deps` for direct imports; a new repo: `map`, `stats`), that edits preview unless `apply=true`, that paths may be absolute or relative to the launch directory, that results carry a `view:` line, and that `state: UNAVAILABLE` means fall back to `rg`.

- **cwd and seq.** The shim's launch directory is sent as `cwd` on every daemon request, with a `seq` that grows by one per `tools/call`. Under the `qartez` name, `--root DIR` sets that directory instead.
- **Tools.** The qartez v0.11.0 names and JSON schemas, captured from the installed binary over MCP: `qartez_map, find, grep, read, outline, deps, stats, impact, refs, calls`; the mutators `qartez_replace_symbol, insert_before_symbol, insert_after_symbol, rename, move, safe_delete, rename_file`; and the build hints `qartez_add_root`, `qartez_workspace`. Not exposed (not in the first cut): `qartez_tools` and the 23 analysis, meta and refactor tools outside this list. Schemas are in `src/mcp_tools.json`. Tool names, parameter names, types, defaults and annotations are qartez's, except that `add_root` / `workspace` make `path` / `alias` optional (so `add_root` requires nothing, `workspace` requires `action`). The descriptions are fdindex's own (research proposal #2): each tool says in its first sentence what it returns, then which sibling to use instead (`find` vs `grep` vs `refs`; `refs` vs `calls`; `impact` vs `deps`; `read` vs `outline`), and nothing it does not do (no FTS5, no tree-sitter, no qartez tools fdindex lacks, no `query` alias on `find`, `with_health` ignored). Each parameter description says its meaning and default in one line; that path parameters take absolute or launch-relative paths is said once, in the instructions. `tests/mcp_descriptions.rs` holds the names to the qartez set and the descriptions to those rules: tool descriptions at most 360 characters, parameter descriptions at most 140, all of them together at most 9,000 (qartez's were 19,698).
- **Results.** A daemon answer is one text content block (the `view:` header included). A refusal is the same block with `isError: true`, reading `state: <STATE>` then the message. An unknown tool name is a JSON-RPC `-32602` error.
- **Daemon down.** If the daemon cannot be reached and cannot be started, the call returns `isError: true` and `state: UNAVAILABLE` plus one line of reason, e.g. `the index daemon is not running (…) and auto-start is disabled`. After a failed start, further calls answer the same at once for 5 s instead of each waiting out a start. `--no-start` (or `FLIGHTDECK_INDEX_NO_START`) disables the start; the default is to start the daemon, as every client does.
- **Reconnect.** A dead connection (the daemon restarted or was killed) is replaced and the call sent again. An applied edit (`apply=true` on a mutator) is never replayed: the shim first asks the daemon `hello` on the existing connection, so a stale one is found before the edit is sent, and a connection lost after the edit was sent is reported as UNAVAILABLE with a note that the file may have been written.

## The `qartez` name

`fdindex` behaves as the qartez alias when `argv[0]`'s basename is `qartez` (a symlink to `fdindex`; `fdindex switchover --apply` installs it, and `qartez-mcp` is accepted as the same name). `qartez mcp` is `fdindex mcp`; `qartez` with no verb starts the MCP server, as qartez does; `qartez find …` is `fdindex find …`; `--root DIR` (first one wins, anywhere on the line) is `--cwd DIR`. Qartez's indexing options before the verb (`--reindex`, `--no-watch`, `--git-depth`, `--db-path`, `--log-level`, `--wiki`, `--leiden-resolution`) are accepted and dropped; `--format json` before the verb is `--json`.

## Service (`fdindex service install|uninstall|start|stop|status|restart`)

Keeps `fdindex daemon` running at login. Nothing about it needs the Flight Deck app.

- **macOS.** A launchd user agent, `~/Library/LaunchAgents/dev.flightdeck.index.plist` (`--label` or `FLIGHTDECK_INDEX_LABEL` changes the label, for tests), loaded into `gui/<uid>` with `launchctl bootstrap`. `ProgramArguments` is the real path of the running `fdindex` (symlinks resolved) plus `daemon`, and `--store` / `--socket` only when they are not the defaults. `RunAtLoad`; `KeepAlive` is `SuccessfulExit=false`, so a crash is restarted (launchd waits its 10 s throttle) and a clean exit (`stop`, or a second daemon finding the lock held) is final. Output goes to `<store>/launchd.log`; the daemon's own log is `<store>/daemon.log`. `PATH` is set to include Homebrew's bin for `git`.
- **Linux.** A systemd user unit, `~/.config/systemd/user/<label>.service`, `ExecStart` as above, `Restart=on-failure`, `WantedBy=default.target`, installed with `systemctl --user daemon-reload` and `enable --now`. Rendered and unit-tested here, not run on Linux yet.
- **install** is idempotent: an unchanged unit that is loaded is left alone; a changed one is unloaded and reloaded. It stops a daemon a client started earlier so the unit's daemon owns the lock and is the one that gets restarted; sessions reconnect on their next call. **uninstall** unloads, removes the unit and stops any daemon left, and is a no-op when not installed.
- **start** runs the unit when installed (`launchctl kickstart`), else starts the daemon unsupervised and says so. **stop** asks the daemon to exit and waits until it has. **restart** is both.
- **status** prints the service (installed, loaded, unit path), the binary, socket and store paths, then from the daemon's `status`: pid, version and protocol, uptime, resident memory and graph-cache use against its budget, the size of the repository stores, request counts, every view (worktree, repository, base, dirty files, requests, idle time) and every build in progress. A stopped daemon is `daemon:   not running` and exit status 3.

## `flightdeck index …`

The `flightdeck` CLI's `index` verb passes everything after `index` to `fdindex` and becomes that process (`execv`): stdio and exit status are fdindex's, and `--json`, `--socket` and `--help` after `index` are fdindex's, not flightdeck's. `fdindex` is found at `$FLIGHTDECK_FDINDEX` (an override that points nowhere is an error, not a fallback), then beside the running `flightdeck` (`Flight Deck.app/Contents/MacOS/fdindex`, where the build puts it), then on `PATH`; none is exit 127 with a message. It does not use the app's control socket, so it works with the app closed. `flightdeck index` alone or `--help` prints the verb's help page.
## Linked views

A manifest that points outside its repository links the repository it lands in (spec §5.3). The link is the **literal path**: `../tessera/designer/src` is whatever worktree sits at that path (the `tessera` main checkout), never a worktree of it paired with this one (requirement 14).

- **Manifests read.** `elm.json` `source-directories`; `tsconfig.json` `compilerOptions.paths` targets (against `baseUrl`, comments and trailing commas allowed) and `references`; `package.json` `file:`/`link:` dependencies (not tarballs) and `workspaces` (up to the first glob); `mix.exs` `path:`; `Cargo.toml` `path =` in a dependency, `[patch]` or `[replace]` table. A target inside the worktree, one that does not exist, and one in a directory that is neither a repository nor a recognised project are not links. Links are recorded per view and re-read when a manifest's content (git blob id) changes, so editing `elm.json` takes effect on the next query.
- **Cross-view resolution.** Elm imports (any source directory outside the worktree) and TypeScript/JavaScript relative imports that climb out of it resolve into the linked view's file. A reference through such an import is looked up in the linked view (`Expression.Node.toString`, `Node.decode`, constructors exposed with `Type(..)` or `(..)`). TypeScript `paths` aliases, `package.json` dependency names and Cargo/mix path dependencies are linked (a pathless search finds their symbols, a mutation is guarded) but their imports are not yet resolved across the link, so `refs`, `calls`, `deps` and `impact` do not follow them.
- **Where it applies.** `find`, `grep` (symbol search) and `read` by symbol with no `file_path` search the caller's view, then the linked views, inside the directories the manifests name (`tessera` is searched in `designer/src` and `typesystem/src`, not whole). `refs`, `calls`, `deps` and `impact` follow imports across views in both directions: from `formula-editor`, `refs Expression.Node.identifierToString` lists the references in `formula-editor` and in `tessera`; `deps`/`impact` on `../tessera/designer/src/Expression/Node.elm` list the `formula-editor` importers. The views on the other side of a link are the ones the answering view's manifests point into (*linked*) and the ones whose manifests point into it (*dependent*): the caller's own checkout when the query named a path elsewhere, plus any view seen before and already indexed. `outline`, `map`, `stats` and `read` of a file range use one view.
- **Labels.** Rows from a view other than the header's carry `[view: <repo> @ <worktree>]` (`find` prints a `View:` line). Lists that span views keep at most 40 rows per view, so a long list in one view does not push the cross-view rows out of the token budget.
- **Build.** A linked or dependent-and-asked-for view that is not indexed builds as part of the request, in parallel with the answering view, and a cold first query from `formula-editor` builds both. One still building at the bound answers from what is stored and says `index: building, N of M files` on its `linked view:` line. Graphs of linked views live in the same cache and under the same budget as any other; nothing is loaded twice.
- **Location.** A resolved graph is shared by the clean worktrees of one commit, but `../lib` is a different directory from each. A graph whose resolution looked outside its root is re-resolved for a worktree that stands elsewhere.
- **Uncommitted edits.** A worktree with local edits answers exactly what a full rebuild of the same content would; `refs`, `calls`, `deps` and `impact` never show a reference still pointing at where a symbol used to be. The overlay re-resolves the edited files, the files that import them, and the files whose references land in them without an import (a Rust call by full path such as `a::m::f()`, or a name re-exported through a barrel file). An edit that leaves everything other files can see unchanged (symbol names, kinds, order, parents and export flags, imports and re-exports, the Elm module name) re-resolves only the edited file, so a body-only edit to a file with hundreds of importers costs no more than any other edit. An edit that adds or removes a definition also re-resolves the files whose unresolved or unique-name references could now bind differently.

### Mutators and links

A mutator writes into the view that answers the lookup and nowhere else.

- No `file_path`, symbol defined only in a linked view: refused (`'x' is not defined in your view …, but a linked view defines it; … never writes into a linked view unless you name a path inside it`), listing the definitions with their views. Nothing is written, preview or apply.
- `file_path` inside the linked view: the mutator plans and writes there as for any view (the answer notes it is not the caller's worktree), **unless** the change would break another view. `rename`, `move`, `safe_delete` and `rename_file` are refused when views that link into the target (the caller's checkout, and views seen before that are indexed) use the symbol or import the file. The refusal lists the files the change would touch in the target view and the sites (`path:line`) in each other view. The first cut does not also rewrite the other checkout: that would edit a view the agent did not name (§5.5), and a half-applied cross-repository rename is worse than a refused one. The agent makes the change in each view, dependent view first.
- A rename of a symbol no other view uses goes ahead. A dependent view that is known but not indexed is not checked; the preview says so in a `warning:`.

## Mutators as built

Arguments beyond the table: `file_path`/`file`/`path` and `kind` narrow the symbol; `rename` takes `old_name`/`new_name` (a qualified `Type::name` also selects); `rename_file` takes `from`/`to`; `move` takes `to_file`; the CLI maps positionals in order (`fdindex rename old new --apply`, `fdindex move sym to/file.rs`). `token_budget` bounds the diff of a preview.

- **Preview by default.** The answer is the view header, `preview: …; nothing written, pass apply=true to write`, notes, `warning:` lines, then `diff -u` per file with absolute paths (created files diff against `/dev/null`).
- **Apply** answers with the header, `applied: …`, one `modified|created|deleted <absolute path>` line per file, and `view updated: N blob(s) re-parsed and the graph recomputed; the next query from <cwd> sees the change`.
- **Which view.** The view containing `file_path` (for `rename_file`, `from`), else the caller's cwd. A name that is defined only in another checkout is refused ("no definition named …", or, for a linked view, the refusal under "Mutators and links"), never a write there. If the path the agent named is in a different worktree from the cwd, the answer adds `note: this is not your worktree (…): the path you named is in …, so that is where the change lands`.
- **Safety.** Every written path must resolve under the view's worktree (symlinks resolved; a symlink target is refused). Files are written temp+rename with their permissions, and each file's bytes are re-checked against what the plan read; if one write fails the earlier ones are put back. A file whose bytes no longer hash to the blob the index parsed is refused (`stale index:`; the daemon replans from a fresh view up to 3 times first). A per-worktree reader/writer gate means a concurrent query sees the worktree before or after a mutation, never between two of its writes. A mutator waits for the complete index (never works from a partial graph) and answers `state: BUILDING` if the wait bound passes.
- **Selection.** Several definitions of the name: refuse and list `kind  /abs/path [Ls-Le] in Parent`. `impl` blocks are not candidates. Rename refuses fields (their uses are not indexed) and Rust modules (use `rename_file`).
- **replace_symbol** replaces the symbol's own line range (attributes and doc comments above it are kept). A symbol that shares lines with other code (`impl X { fn f() {} }`) is replaced by columns. `new_code` must start with a definition introducer for the language (after attributes and comments), or be a member/variant for kinds that have none.
- **rename** rewrites the definition, every reference the graph resolved to it (line + name + qualifier), import lists naming it (following re-exports), the Elm `module … exposing` header, and members reached through a renamed type (`Store::new`). Aliased imports keep their alias. Occurrences in strings and comments are never touched. Files involved that still contain the old name afterwards are listed as a warning (a shadowing local, a template literal, a destructured dynamic import).
- **move** (Elm, TypeScript/JavaScript, Rust): cuts the definition with its doc comment and attributes, adds it to `to_file` (created if missing: Elm module header and name from the source directory, Rust `mod` line in the parent module file), copies the imports the moved code needs, repoints every importer (exposing lists, qualified uses, `import { x } from`, `use` paths), imports it back into the source if the source still uses it, and exposes what the moved code reaches back for. Refused: Elm moves whose code needs a sibling the source uses back from it (an import cycle); non-exported siblings in TS/Rust; non-top-level symbols.
- **rename_file** (Elm, TypeScript/JavaScript, Rust): Elm rewrites the `module` line, `import`s, and unaliased qualified uses, and `exposed-modules` in `elm.json`; TS/JS rewrites relative specifiers in importers and in the moved file's own imports; Rust rewrites the parent `mod` line and `use`/qualified paths, within one directory, refusing `mod.rs`, `lib.rs`, `main.rs` and modules with child directories.
- **Other languages**: `rename`, `replace_symbol`, `insert_*` and `safe_delete` work from index facts; `move` and `rename_file` refuse naming the gap.
- **safe_delete** counts references from outside the symbol (and its constructors) plus import lists naming it, refuses unless `force`, takes doc comments with it, and removes the name from an Elm module's `exposing` list.

## The acknowledgement gate (for the switch-over step)

Today's gate is the `qartez-guard` binary, registered as a `PreToolUse` hook on `Edit|Write|MultiEdit` and `Glob|Grep` in `~/.claude/settings.json` and `~/.claude-radify/settings.json`. Observed as a black box:

- It denies an `Edit` of a file whose PageRank or blast radius is over `--pagerank-min` / `--blast-min` (env `QARTEZ_GUARD_PAGERANK_MIN`, `QARTEZ_GUARD_BLAST_MIN`) unless an ack for that file is younger than the TTL (`--ack-ttl-secs`, env `QARTEZ_GUARD_ACK_TTL_SECS`; the default is between 5 and 10 minutes, probably 600).
- Acks live in `<project_root>/.qartez/acks/` where `project_root` is `$CLAUDE_PROJECT_DIR` or auto-detected (`--project-root`). A linked worktree has its own `.qartez/` (for example `flight-deck-worktrees/canvas/.qartez/acks`), so acks are per worktree today.
- One file per path. Name: the FNV-1a 64-bit hash (offset `0xcbf29ce484222325`, prime `0x100000001b3`, over the UTF-8 bytes of the path relative to the project root, no newline), as 16 lowercase hex digits. Content: `<unix seconds>\n<relative path>\n`. All 40 files in the flight-deck checkout match that name rule.
- Age is the file's **mtime**, not the epoch in its content (an ack with a 5000 s old epoch and a fresh mtime was accepted; one with a fresh epoch and an old mtime was denied).
- The guard also reads PageRank and blast radius from `<project_root>/.qartez/index.db` (`--db`), so the guard itself must be replaced or pointed at the daemon at switch-over; writing compatible acks alone does not retire it.

To stay compatible per view, the new `impact` tool writes `<view worktree>/.qartez/acks/<fnv1a64(relative path)>` with that content on every call. The view's worktree is the right root: it is what `$CLAUDE_PROJECT_DIR` is for a session started in that worktree.


## Switch-over (spec §11a step 8), as built

`fdindex guard`, `fdindex session-start` and `fdindex switchover` replace `qartez-guard`, `qartez-setup --session-start` and the hand edits of every agent config. Sources: `src/guard.rs`, `src/session_start.rs`, `src/switchover.rs`, `src/ack.rs`, `src/textedit.rs`.

### `fdindex guard` (PreToolUse hook)

Same observable contract as the installed `qartez-guard`, characterised black-box: Claude Code's PreToolUse JSON on stdin; stdout is empty to allow or `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"…"}}` plus a newline to deny; the exit status is always 0. `scripts/guard-parity.sh` runs both on the same inputs (31 cases, all matching in decision and wording).

- `Glob`/`glob`, `Grep`/`grep` and Gemini's `grep_search` are denied in a project whose index is ready, whatever the pattern (the old hook words `grep_search` like `Glob`). Messages are the old ones, naming `qartez_map`, `qartez_find`, `qartez_grep`.
- `Edit`, `Write`, `MultiEdit`, `replace`, `write_file` of a file whose PageRank is at least `--pagerank-min` / `QARTEZ_GUARD_PAGERANK_MIN` (0.05) or whose blast radius is at least `--blast-min` / `QARTEZ_GUARD_BLAST_MIN` (10) are denied unless an ack is no older than `--ack-ttl-secs` / `QARTEZ_GUARD_ACK_TTL_SECS` (600; `QARTEZ_ACK_TTL_SECS` also works). The message lists the exceeded thresholds (PageRank first) and the file's three top symbols. A file the index does not know is not guarded. `QARTEZ_GUARD_DISABLE` other than empty, `0` or `false` turns it off. `--db` is accepted and ignored.
- Facts come from the daemon through an internal `guard` request (`{"state":"NONE|BUILDING|READY","worktree","in_index","rel","pagerank","blast","hot":[…]}`): the view that holds the file, ranks from its graph, blast radius within that view. The old hook looked for `.qartez/index.db` upward from the file; this one does not need a project directory at all, so `$CLAUDE_PROJECT_DIR` and `--project-root` only stand in for a missing `cwd`.
- **The index never blocks an agent.** Daemon not running or not answering (2.5 s), or the view still building (1.5 s wait): the call is allowed and stderr says why. The hook never starts a daemon.
- Acks are written by `impact` (`src/ack.rs`) into `<view worktree>/.qartez/acks/`, in the format above, so the old guard and the new one accept each other's.
- One deliberate difference: a relative `file_path` is resolved against the call's `cwd`; the old hook resolved it against its own working directory (Claude Code always sends absolute paths).

### `fdindex session-start`

`qartez-setup --session-start` prints nothing and, in the background, indexes the session's project and checks GitHub for a newer qartez (observed in a temp HOME: `~/.qartez/last-update-check`, `~/.cache/qartez-mcp/session-index.log`). `session-start` keeps the useful half: it starts the daemon if needed and starts the cwd view's build without waiting (the `guard` request with no file does that, and answers `NONE` for a directory that is no project, so a session in `~` indexes nothing). It prints only when an agent should act: the daemon could not be started or did not answer within 4 s (`state: UNAVAILABLE`, fall back to rg), or the view is still building. Exit status 0 always.

### No `.qartez/status.json`

The daemon is machine-wide, so a per-project status file would be written into every worktree and go stale; the results carry the state instead (`view:` header with `index: building, N of M files`; `state: BUILDING|UNAVAILABLE|…` on refusals), and `fdindex status` describes the daemon. The skill draft says so.

### `fdindex switchover`

`--dry-run` (the default) prints every file and change, `--apply` does it, `--rollback` undoes the last apply, `--list-old-dbs [root…]` lists `.qartez/index.db` files with sizes (default root `~/Projects`) and deletes nothing. `--home`, `--store` and `--no-service` exist for rehearsal. See the module comment of `src/switchover.rs` for exactly what changes, and `scripts/switchover-rehearsal.sh` for the round trip on copies of the real files.

## Memory

`--memory-mb N` (default 1536) is the RSS the daemon aims to stay under. It maps to a limit on live heap, `(N - 192 MB) / 1.2`, and to the default graph budget of the same size; `--graph-budget-mb` alone raises the target to fit it. `status` reports `rss_bytes`, `memory_target`, `heap_bytes`, `heap_peak_bytes`, `vm` (macOS: resident, internal, reusable, footprint) and `graphs.heap_limit`. The default is the figure the graph budget used to be: 1.5 GB holds about 30 tessera-size graphs, one hot worktree per agent for thirty agents; 1 GiB holds 19 and cycles its cache under that load.

Measured on tessera (86 to 93 worktrees, the count grew while measuring): every worktree queried one after another, twice; then 30 clients (reads, builds, applies in throwaway worktrees) for 90 s. The host's load average was 80 to 165 throughout, so latencies compare roughly:

| | RSS after sweep | RSS peak, 30 clients | live heap peak | graphs cached | evictions (sweep x2 / mixed) | find p50 sweep 1 / 2 / mixed |
|---|---|---|---|---|---|---|
| before: 1.5 GB graph budget | 1803 / 1816 MB | 2636 MB | 2071 MB (earlier run) | 41 | 155 / 1982 | 568 / 297 / 682 ms |
| `--memory-mb 1536` (default) | 1424 / 1441 MB | 1660 MB | 1206 MB | 30 | 178 / 742 | 814 / 319 / 3601 ms |
| `--memory-mb 1024` | 1023 / 1038 MB | 1165 MB | 810 MB | 19 | 197 / 452 | 834 / 340 / 8781 ms |

Reading the latency: a hot find is 7 ms either way, and the second sweep is within noise. What costs is the mixed run, where 30 clients pick among about 95 worktrees at random: with fewer graphs cached more requests rebuild one (0.2 to 0.4 s on a quiet machine, seconds on this loaded one), and builds now queue for four slots instead of all running at once. Machines that want the old latency under that load can pass `--memory-mb 3072`.

**Shared blocks.** The graphs of one repository share their per-file resolutions. Each file's resolution (imports, every reference's target and confidence, file edges) is a block, hash-consed by content in a per-repository table, so a graph of a nearby commit points at the blocks that came out the same instead of holding copies; file indices follow a per-repository numbering so that equal blocks really are equal (a path keeps its index, a graph has a dead slot for each numbered path it lacks, and a view under a quarter of the numbering's size is numbered on its own). Keyed by content, a block whose unique-name fallback answer changed is simply a different block: nothing is shared stale. Each graph's name index and incoming-reference index are sorted arrays rather than hash maps. `status` reports `graphs.blocks` and `graphs.block_bytes` (counted once, inside `graphs.bytes`). Answers are unchanged: a graph built this way has the same fingerprint as one built alone.

Measured on the 42 tessera worktrees of distinct commits, queried in turn by `map` with `--graph-budget-mb 100000 --no-watch` (44 graphs: two worktrees are dirty), blobs already stored, two runs each, load average 21 to 32:

| graphs cached | RSS before / after | live heap before / after | footprint before / after |
|---|---|---|---|
| 1 | 153 / 148 MB | 99 / 94 MB | 113 / 106 MB |
| 11 | 611 / 400 MB | 478 / 296 MB | 486 / 271 MB |
| 44 | 1807 / 806 MB | 1494 / 641 MB | 1473 / 505 MB |

The 44 graphs hold 100,876 file resolutions, of which 18,688 are distinct (210 MB); the facts of the 42 commits are another 254 MB. A graph build costs 5 to 10% more (min of 7 builds of tessera at 81f973be6 with facts in memory: 196 to 207 ms before, 211 to 228 ms after, load 29 to 30), for hashing and comparing blocks.

Where the memory went (before): 1327 MB live heap at 1512 MB charged (graphs and their facts, 12.4 million allocations); kept views of 85 worktrees 93 MB; 130 to 190 MB resident that is not live heap at all (a daemon holding one graph is at 440 MB RSS with 200 MB live); and, under concurrency, 700 MB of transient peak from builds running together plus graphs evicted from the cache while requests still held them, which freed nothing and were not counted. Allocator retention is real but not recoverable from inside the process on macOS: `malloc_zone_pressure_relief` ran 83 times without changing RSS, swapping in mimalloc (with `mi_collect`) was 200 MB worse at one graph, and the kernel's own accounting (`vm`) marks 85% of the resident pages reusable, which is why an RSS-triggered eviction loop would evict everything and free nothing.
